# 社区讨论作者身份自动补齐设计

## 目标与范围

现有线上讨论中有已保存正文、但 `author`、`handle`、`avatar_url` 为空的来源。更新网站代码不会自动改变这些 Supabase 记录。本阶段要让旧记录在云服务器更新后逐步补齐身份，也让后台以后添加的每条手动推文链接使用同一套身份提取与补齐流程。仅修复身份元数据，不重抓整棵评论树，不改动原文、译文、讨论标题或人工描述。手动链接的父子关系与展开界面是下一阶段的独立设计和实施。

成功标准：在 Twitter241 返回可核实的作者资料时，主题帖和回应的昵称、@账号与头像均持久保存并在列表、详情页显示；旧记录无需逐条人工刷新；已完整的记录每 24 小时重新核对同一作者的昵称和头像；服务重启后继续处理；无法核实资料时绝不把别人的头像或昵称写入。

## 已知事实与诊断边界

- 本站通过 `server/discussions/runtime.ts` 的 Twitter241 `/tweet?pid=...` 抓取推文；`server/communityDiscussion.ts` 当前读取部分 `core`、`legacy` 与 `avatar` 路径。后台新建接口不接受人工填写作者身份。
- 2026-10-20 只读检查公开 API 时，已有讨论保存了作者名、账号和头像；另一些讨论及回应保存为空。因此服务具有获取这些字段的能力，但还不能断言缺失记录的具体根因。
- 本地未配置 Twitter241 密钥，尚未取得问题推文的原始响应。实施时先验证一条缺失来源的响应结构；若仍无法取得真实样本，则只依据可测试结构实现解析，不宣称已证实上游对该来源返回完整身份。
- 昵称和头像是重新查询时的账号资料，不承诺还原发帖当时的历史资料。仅有推文 URL 中的账号名不足以证明当前同名账号仍是原作者。

## 方案选择

推荐把有界、非阻塞的身份补齐队列放在常驻 `pearl-web` 服务中，复用一个身份解析器。它不依赖访客请求，也不依赖 `pearl-translation` 的翻译配置。服务器按仓库的 systemd 文档运行一个网站进程；队列仍应使用数据库原子领取和过期租约，避免误开多实例或重启时重复抓取。

备选一是部署后由同事运行一次性脚本，操作少但未来新增记录、暂时失败的请求都不会自动修复。备选二是增加专门的 `pearl-identity` systemd 服务，隔离性好，但增加需要安装、启用和监控的服务。当前规模下，网站进程内的受限队列更贴合现有部署方式。

## 数据流与边界

1. 后台添加主题或回应时，仍先按推文 ID 抓原文。身份提取器从与该推文对应的作者对象读取稳定用户 ID、昵称、账号和头像，不从引用帖、转帖或嵌套的其他推文误取作者。解析兼容已观察到的 `core`、`legacy` 结构，并用测试固定每种结构。
2. 若推文正文存在而作者资料不完整，仍保存正文。先尝试 Twitter241 的 `/tweet-v2?pid=...`；只有拿到能与该推文作者关联的稳定用户 ID 或上游明确的作者对象时，才允许通过用户资料接口补查并写入昵称、账号、头像。URL 中的账号名仅用于显示兜底，不作为写入他人资料的唯一证据。
3. 数据库增加作者稳定用户 ID、独立的身份同步时间、下次尝试时间与领取租约字段。迁移不清空或重写现有来源；迁移前的缺失身份记录自动成为待处理项。身份完整的记录也按 24 小时周期再次到期，而不是每次轮询都付费查询。
   旧记录首次从推文确认稳定用户 ID 时，仅补空字段，五分钟后再查询当前用户资料；只有已绑定 ID 的当前资料可覆盖已有昵称、账号和头像，避免旧推文资料倒退已保存的信息。
4. `pearl-web` 启动后异步扫描少量到期记录，优先处理缺失身份的旧记录，原子领取后串行或低并发查询 Twitter241。只有上游作者用户 ID 与已存 ID 一致（旧记录尚无 ID 时，先从该推文本身取得 ID）才更新有值且变化的昵称、账号、头像；上游空值不得擦除现有值。写入时保留 `blocks`、`translationZh`、`fetched_at`、`last_attempted_at`、`fetch_status`、标题与描述；并发刷新不能把更新后的身份改回旧值。
5. 请求超时、配额、暂时不可用或仍缺字段时，记录下一次尝试时间并退避；轮询有批量上限，不阻塞 HTTP 请求。日志仅报告来源 ID、结果与安全错误类别，不输出密钥或完整上游响应。停止服务时不留下永久占用的任务，租约到期后可接续。
6. 公共 API 继续提供已保存的身份；页面在昵称缺失时展示可从原推文 URL 确认的 `@账号`，头像缺失时展示默认头像，不将“作者未提供”误作已确认身份。前端不直接调用 Twitter241。

## 测试与部署验收

- 用测试覆盖普通推文、长文、不同用户结构、引用帖干扰、无作者对象、用户查询成功和不匹配，以及旧记录仅更新空身份字段的行为。
- 用存储层测试验证原子领取、租约过期、24 小时后重新到期、失败退避、并发刷新、上游空值不擦除旧身份、原文与译文完全保留；用服务测试验证创建和周期核对共用身份解析逻辑。
- 本地运行相关测试及生产构建。由于本地没有有效 Twitter241 环境变量，真实缺失推文的上游返回只能在具备密钥的受控环境中验证；上线后以公开 API 的缺失字段数量和服务日志确认补齐结果，而不是仅凭页面截图宣称全部修复。
- 同事的更新步骤：从 GitHub 拉取代码，先执行本次新增的 Supabase 迁移，再运行 `npm ci`、`npm run build` 并重启 `pearl-web`；`pearl-translation` 可照常运行。服务器的 `/etc/pearl/pearl.env` 必须保留有效的 `TWITTER241_API_KEY` 和 Supabase 服务端配置，密钥不得进入 GitHub。部署文档需列明进度检查、故障排查与回滚方式。
- 若上游对某条推文始终不给可核实的作者资料，该记录保持账号/默认头像兜底并继续受限重试，不能承诺 100% 自动恢复真实头像。
